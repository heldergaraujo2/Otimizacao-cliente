# SECURITY_AND_LICENSES

## 2. Game data and trademarks (the important part)

- MU Online, its client, models, textures, sounds, maps and the `data/*.pak` archives are the property
  of **Webzen** (and respective rights holders). Open-source licences on *code* do not grant rights
  over *game data*.
- Therefore: **no game data, no client binaries, no extracted assets and no cracks enter this
  repository.** Tests use fixtures generated by our own code
  (`packages/mu-formats/src/testing/fixtures.ts`).
- Game data is read at runtime from a directory the contributor provides
  (`MU_REENGINEER_DATA`, git-ignored as `assets-local/` and `MU-REENGINEER-DATA/`).
- If this project is ever distributed, it must ship without game data, with documentation that the
  user must own a licensed copy — and the final decision on distribution is the user's, per the
  master command §9.

## 3. Dependencies and supply chain

- Runtime dependencies: **none** in `packages/mu-protocol` and `packages/mu-formats` (Node built-ins
  only: `node:zlib`, `node:test`, `node:assert`). This keeps the toolchain reproducible offline and
  the attack surface small.
- Dev dependencies: `typescript`, `@types/node` (pinned in the root `package.json`; lockfile
  committed).
- Adding a dependency requires: licence check, size/activity check, and a note in
  `project/DECISIONS.md`. Native/binary dependencies are avoided unless there is no alternative.
- No install scripts, no post-install downloads, no unknown binaries are executed. The reference
  repositories are cloned as *sources* and never run.

## 4. Handling untrusted input (the parsers are the attack surface)

Game files and network packets are untrusted data. Rules followed in this code base:

- Every parser validates length and count fields **before** allocating or indexing (e.g. mesh/vertex
  counts are range-checked and fail with `invalid mesh count: …`), so a malformed file produces an
  error instead of a crash/out-of-bounds read.
- Unsupported cipher algorithms throw `UnsupportedCipherError` naming the algorithm — never fall back
  to "best effort" decryption of unknown data.
- The server must treat every client packet as untrusted: validate lengths, reject unknown codes and
  sub-codes, rate-limit, and never trust client-side movement/targets (server authority — to be
  implemented and tested in `packages/mu-server`).
- No dynamic code evaluation, no `eval`, no shelling out to external tools with user-controlled
  arguments.

## 5. Secrets and privacy

- No tokens, passwords, keys, credentials or personal data in the repository, ever. `.env*`, `*.key`,
  `*.pem`, `credentials.json` are git-ignored.
- The client identifiers used for protocol compatibility (client version `1.04d`, serial
  `0123456789ABCDEF`, XOR3 key, SimpleModulus reference keys, LEA/BMD key) are **protocol constants
  published in the reference implementations**, not secrets of ours; they are documented as such
  where they appear in code.
- Test accounts are synthetic. Real player data must never be committed; if a future feature needs
  persistence, it goes to a local, git-ignored store.

## 6. Reporting and review checklist (before each commit)

1. `git diff` reviewed: no secrets, no game assets, no binaries, no build output.
2. New files' licences compatible and attributed.
3. Tests for new behaviour actually executed; results recorded.
4. Anything unverified is written down as a gap (never as "done").
